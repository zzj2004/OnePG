# M3 局域网联机设计

日期：2026-09-04 ｜ 对应里程碑：M3 ｜ 前置：M0/M1/M2（16 项自动化测试全绿）
验收标准：两台设备连同一 WiFi，一台创建房间、一台输房间码加入，能完整打完一局，体感延迟可接受。

## 1. 为什么现在联机反而"便宜"了

M0 立下的铁律——"固定步长确定性模拟：同样输入必出同样结果"——在 M3 全部兑现：

- 联机时**只传输每帧的按键位**（1 字节），不传任何画面/位置数据
- 两台电脑各自运行同一个模拟核心，输入一致 → 对战过程逐帧一致
- **模拟核心零改动**：联机层全部在核心之外（传输、协议、同步调度）

## 2. 同步方案：锁帧同步 + 输入延迟（不用回滚式）

| 方案 | 原理 | 适用 |
|---|---|---|
| **锁帧同步（本方案）** | 双方每帧互发按键，收齐才推进下一帧 | 局域网延迟 1~10ms，完美适用 |
| 回滚式（GGPO） | 猜测输入先跑，错了时光倒流重算 | 跨公网 50ms+，复杂度高一个数量级 |

- **输入延迟 3 帧**（50ms）：本地方案按下后 3 帧才生效，正好给网络传输留出时间，局域网体感接近零延迟
- 收不到对方输入时不猜测、不假推——**宁可画面停住也不让两台电脑算岔**（停住会显示"等待对手"）
- 每 60 帧互发一次**状态校验和**：不一致立即显示"不同步"警告（诚实暴露，不静默掩盖）

## 3. 连接方案：房间号（立项文档第 6 节的兑现）

```
房主：标题按4 → 创建房间 → 屏幕显示 4 位房间码（如 K7QF）
对手：标题按4 → 加入房间 → 输入 K7QF → 连上
```

- 撮合握手走 PeerJS 公共服务（免费、只传"双方怎么找到彼此"的地址信息）
- 握手完成后，WebRTC 在同一局域网内**直连**（对战数据不离开你们的 WiFi）
- 限制（立项文档已如实记录）：双方都需联网完成握手；完全断网的两台电脑无法自动互相发现（浏览器安全限制），单人/同键盘双人不受影响

## 4. 联机流程与分工

```
房主：创建房间 → 对手加入 → 选自己角色 → 给对手选角色 → 选地图 → 按 F 开始 → 倒计时 → 对战
对手：加入房间（输码）→ 等待主机配置 → 倒计时 → 对战（自己控制蓝色方）
```

- 房主决定全部配置（含对手用哪个角色）——M3 简化，双方各自选人留到 M4
- 连接建立后配置通过数据通道同步；版本不一致会拒绝开战
- 断线处理：数据通道断开 → 显示"对手已断线"→ 回标题（不做断线重连，如实记录）

## 5. 技术分层

```
src/net/
  protocol.ts   输入位编码(1字节7个键)、状态校验和(FNV-1a)、版本常量、消息类型
  transport.ts  NetTransport 接口 + 两个实现：
                PeerTransport（PeerJS 房间号，真实局域网）
                LoopbackTransport（BroadcastChannel，同机双标签测试用，协议栈完全一致）
  lockstep.ts   NetSession：输入缓冲、推进门控、等待计数、校验和交换
```

- 两个传输实现走同一套协议和同步逻辑——**本地双标签能跑通 = 局域网就能跑通**，这是可测试性的关键
- 对局内每帧：本地方案 → 会话缓冲 → 双方输入齐 → step(模拟, [本地, 远程])

## 6. 已知简化（诚实记录）

1. 不做断线重连；不做旁观者
2. 输入延迟固定 3 帧（不做自动测延迟自适应）
3. 房间码靠 PeerJS 公共撮合服务，若该服务 someday 关停，需自建撮合（代码里留了配置位）
4. 校验和不一致只警告不自动修复——修复方案（状态回滚重同步）超出本阶段

## 7. 自动化测试计划（新增 src/tests/net.ts，与原有 16 项一起跑）

1. 位编码往返：7 个键任意组合 → 1 字节 → 解码一致
2. 校验和：同一状态两遍哈希一致；改任意一个位置数值哈希必变
3. 双会话内存总线：两个 NetSession 通过内存总线互发，同一输入脚本推进 600 帧，
   两个模拟的状态校验和逐帧一致
4. 输入延迟语义：前 3 帧用预填空输入推进；远端输入缺失时推进暂停
